# Техническое задание на учебный проект “Платёжная система”

Цель проекта \- продемонстрировать использование различных возможностей фреймворка Laravel при разработке фин.тех проектов. Разрабатывается исключительно бэкенд-часть приложения. Работаем с воображаемым фронтом. Проверка \- через систему тестирования Laravel и прямые Http-запросы через Postman. API-вызовы получают и возвращают данные в виде JSON.

## Общее описание

Проект представляет собой реализацию традиционной системы приёма платежей через редирект.

Система мерчанта, при готовности выставить счёт своему покупателю, с помощью вызова API создаёт платёжную ссылку, и перенаправляет покупателя по ней. Сам платёж происходит на стороне платёжной системы

Первая версия проекта не предполагает эмуляцию базового API. Покупатель просто нажимает кнопку “Оплачено” или “Провал оплаты”.

Платёжная система должна соответственно пометить платёж и реализовать скрытый обратный вызов (web-hook) к системе мерчанта для информирования о результатах оплаты.

Предусмотреть идемпотентность везде, где она важна. 

## Публичная часть приложения

### Аутентификация

Реализуется с нуля (без использования Laravel Breeze и других пакетов из коробки). Регистрация и вход мерчанта происходит через указание логина и пароля. При регистрации почту необходимо подтвердить. После входа мерчанту доступен его кабинет. 

Для логина предусмотреть защиту от перебора паролей \- не более 3 неудачных попыток за 30 минут

### Управление аккаунтом

Нужно поддерживать смену пароля и смену email с переподтверждением

### Кассы

Для приёма платежей мерчант создаёт одну или несколько касс. Каждая касса имеет имя, которое должно быть уникальным в пределах мерчанта. Каждой кассе назначается автоматически сгенерированный секретный ключ, который используется для подписей запросов от мерчанта и запросов к мерчанту. Для каждой кассы указывается URL перенаправления после успешного или провального платежа, а так же ендпоинт для обработки веб\-хуков

Необходимо реализовать возможность добавлять, редактировать и управлять кассами. 

Необходимо реализовать просмотр платежей по каждой кассе и в целом по пользователю. 

Так же необходимо реализовать просмотр статистики по кассам:

* Количество платежей по дням, месяцам, годам

* Средний чек за день, год, месяц

### Подготовка платежа мерчантом

Процесс приёма платежа начинается на стороне мерчанта. Мерчант подготавливает следующий запрос, и направляет его в API  платёжной системы

* ID кассы в платёжной системе

* Описание платежа

* Внутренний ID платежа/заказа в системе мерчанта

* Сумму в виде целого числа в тийинах

* Запрос должен быть подписан секретным ключём

Платёжная система регистрирует у себя запрос и создаёт под него ссылку для оплаты, которую возвращает мерчанту. Мерчант должен перенаправить своего клиента по этой ссылке

Ограничение: на один внутренний id заказа может быть создана только одна ссылка

#### Процесс подписи запроса

1. Отсортировать все ключи по алфавиту

2. Собрать строку вида “ключ|значение|ключ|значение|”

3. Полученную строку подписать HMAC с использованием хеш-функции sha-256

### Обработка платежа на стороне платёжной системы

Первая версия предполагает что фронт просто показывает две кнопки: “Оплачено”, “Провал”. Нужно обработать каждую из них, поставив платежу соответственный статус, и инициировать информирование клиента через веб\-хук.

Предусмотреть потенциальную возможность retry со стороны клиента (идемпотентность запроса)

При информировании через веб\-хук предусмотреть возможность временного сбоя на стороне мерчанта, реализовать до 10 повторных вызовов через увеличивающиеся в геометрической прогрессии промежутки (через 30 секунд, 1 минуту, 2 минуты, 4 минуты и так далее)

### Вывод мерчантом своих денег в свой банк

Мерчант должен иметь возможность подавать заявки на вывод, указав банковские реквизиты для перевода. При этом необходимо также предусмотреть защиту от повторных вызовов с фронта, используя уникальные ключи идемпотентности, которые должен предоставить фронт при формировании заявки.

Заявки обрабатываются администратором, и мерчант должен иметь возможность видеть, какие заявки уже обработаны

### Тикетная система поддержки

Нужно реализовать возможность создавать тикеты для системы поддержки, которые потом сможет видеть и на которые сможет отвечать администратор. Тикет состоит из заголовка и сообщения. В тикет можно писать, пока он не закрыт администратором. Статусы тикета:

* Новый  
* В работе  
* Закрытый

## Админ панель

### Роли и права

Необходимо реализовать две основные роли

* Администратор \- имеет полный доступ ко всей системе. Может блокировать пользователей  
* Агент поддержки. Имеет доступ только для чтения к системе. Но может отвечать на тикеты.

### Управление пользователями

В административной панели должна быть предусмотрена возможность просмотра всех пользователей, с фильтрацией по дате регистрации, частичному совпадению e-mail, названию или ID кассы. Нужно так же предусмотреть возможность забанить любого пользователя, и разблокировать его обратно. После бана пользователю должна быть доступна только переписка с поддержкой. 

Для каждого пользователя нужна возможность просматривать его кассы, баланс на них. 

### Просмотр платежей

Нужна возможность просматривать все платежи, совершённые в системе, с фильтрацией по пользователю, по датам, по статусу. 

### Статистика

Нужно сделать возможность получения статистики, какая касса/какой пользователь даёт какой доход нашей платёжной системы. Будем считать, что 10% всех успешных платежей \- это наш доход.

### Поддержка

Админ должен иметь возможность видеть тикеты и отвечать на них
