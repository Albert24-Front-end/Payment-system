# План реализации статистики платежей (версия 2)

Статус: план для реализации с ИИ-агентом; код по этому документу ещё не проверен.

## 1. Источники, границы и правила для агента
**Само задание: [AI tasks/statistics.md](../AI%20tasks/statistics.md).
**Спецификация: [AI specification/base-spec.md](../AI%20specification/base-spec.md).
**Правила проекта: `.codex/development.md`, `.codex/testing.md`, `.codex/runtime.md`, and `.codex/project-overview.md`.
**Требования из ТЗ:** мерчант может иметь несколько касс; нужен просмотр статистики **по кассам** — количество платежей и средний чек по дням, месяцам, годам. В административной части нужно видеть, **какая касса и какой пользователь** приносят платёжной системе доход. По условию доход равен 10% успешных платежей. Денежные суммы платежей хранятся целыми тийинами. Существуют администратор с полным доступом и агент поддержки с правами чтения (и ответом на тикеты). После бана пользователю доступна только переписка с поддержкой. API принимает и возвращает JSON, реализация проверяется тестами и HTTP-запросами.

**Границы:** только API для чтения имеющихся платежей. Не изменять платежи, баланс, фактические комиссии, заявки на вывод, webhook, существующие API и модель расчётов. Не добавлять UI, планировщики, кэш, витрины статистики или универсальную аналитику.

| Пустые периоды | ТЗ не определяет формат | Для выбранной кассы вернуть все календарные периоды диапазона, заполняя нулями. Для каждого объекта в административном отчёте также заполнять пропуски. |

Особенно явно согласовать семантику успешного платежа, округления и доступ поддержки; не скрывать расхождения в коде.

## 2. HTTP-контракт первой версии

Использовать `Terminal`, `terminal`, `terminal_id` во всех слоях и примерах. Сохранить текущие префиксы маршрутов, аутентификацию, middleware бана и принятую структуру ответа.

### Мерчант

`GET /api/terminals/{terminal}/statistics?period=day&from=2026-09-01&to=2026-09-02`

- `period=day|month|year`, `from`, `to` обязательны. Нет `user_id`, `page`, `per_page` или произвольного `terminal_id` в query: касса уже указана в пути.
- Доступ только владельцу кассы и тем ролям, которым он реально предусмотрен текущими правилами. Выборку и авторизацию организовать так, чтобы нельзя было получить чужие данные через подмену ID. Для чужой кассы вернуть согласованный с проектом статус (403 при авторизованном route binding либо 404 при ownership-scoped lookup); закрепить **один** вариант тестом. Для несуществующей — 404.
- Не полагаться только на то, что middleware/route binding защитит SQL-запрос: ограничить запрос платежей ID авторизованной кассы.

Пример (имена ключей подогнать под принятый API, сохранив типы и смысл):

```json
{
  "success": true,
  "data": [
    {"period_start": "2026-09-01", "payment_count": 2, "payment_amount": 15001, "average_check": 7501},
    {"period_start": "2026-09-02", "payment_count": 0, "payment_amount": 0, "average_check": 0}
  ],
  "meta": {"period": "day", "from": "2026-09-01", "to": "2026-09-02", "timezone": "UTC", "money_unit": "tiyin"}
}
```

`payment_amount` полезен для проверки средней суммы, но не обязателен по ТЗ; если в API проекта принято отдавать только требуемые метрики, убрать его из публичного ответа, сохранив сумму внутри агрегации. `period_start`: `YYYY-MM-DD` для дня, первое число месяца для месяца, 1 января для года. Граничные месяц/год включать, даже если `from/to` внутри них; считать платежи только в точном диапазоне дат.

### Административный отчёт

`GET /api/admin/statistics?group_by=terminal&period=month&from=2026-01-01&to=2026-09-30`

- Обязательны `group_by=terminal|user`, `period`, `from`, `to`. Не добавлять пока фильтры `user_id`, `terminal_id`: их нет в ТЗ статистики. Отдельные фильтры других разделов админки не означают, что они требуются здесь.
- Использовать явное право просмотра статистики (`statistics.view`) и действующий механизм ролей. Префикс `/admin` сам по себе не является проверкой прав. Миграцию permission делать только если текущий проект действительно использует permission-записи; не редактировать старые миграции. Назначить право ролям чтения согласно проверенному правилу выше.
- Для массива сущностей использовать привычную проекту пагинацию; если существующего стандарта нет, `page` и `per_page` с default 25, max 100. Сначала определить подходящие сущности с успешными платежами за диапазон, затем применить стабильную сортировку и пагинацию, потом **одним** агрегирующим запросом получить периоды текущей страницы. `total` означает число подходящих сущностей, не число платежей. Нельзя пагинировать строки «сущность × период».
- Сущность в `group_by=terminal`: ID, безопасное отображаемое имя кассы, при необходимости ID владельца. В `group_by=user`: ID и разрешённое проектом отображаемое поле пользователя. Не отдавать `secret_key`, полную модель, токены или лишние персональные поля.

```json
{
  "success": true,
  "data": [
    {
      "entity_id": 12,
      "entity_label": "Shop A",
      "periods": [
        {"period_start": "2026-09-01", "payment_count": 2, "payment_amount": 15001, "income": 1500},
        {"period_start": "2026-10-01", "payment_count": 0, "payment_amount": 0, "income": 0}
      ]
    }
  ],
  "meta": {"group_by": "terminal", "period": "month", "from": "2026-09-15", "to": "2026-10-10", "timezone": "UTC", "money_unit": "tiyin", "current_page": 1, "per_page": 25, "total": 1, "last_page": 1}
}
```

Пример иллюстрирует частичные месяцы. Выбор конкретных JSON-ключей сверить с уже опубликованными ответами; после выбора зафиксировать feature-тестами и краткой документацией API.

## 3. Проверка входа и границы времени

- FormRequest проверяет допустимый `period`, обязательные реальные календарные даты в формате `Y-m-d`, `from <= to`, допустимый `group_by` только для админа и параметры пагинации только для админа. Не принимать неизвестные параметры, которые могут притворяться фильтрами области данных; `user_id` мерчанта не должен расширять выборку.
- Предложенное ограничение — не более **366 календарных бакетов** на один запрос; при превышении 422 с понятной ошибкой. Число считать календарным шагом выбранной стратегии, а не разностью дней для месяца/года. Это защита размера ответа, не требование ТЗ; не усекать данные молча. При пагинации админа ограничение действует на каждый ряд.
- Построить начало `from` и исключающую верхнюю границу `to + 1 day` в согласованном часовом поясе. Для `timestamp with time zone` PostgreSQL группировать явно в выбранной зоне; для `timestamp without time zone` установить, какие значения там хранятся, и использовать эквивалентное выражение. Проверить реальный SQL на работающем PostgreSQL: `date_trunc()` может группировать по session timezone. Предикаты по датам оставить на исходном `payments.created_at` для возможности применения индекса.
- Не использовать `whereBetween(created_at, ['2026-09-01', '2026-09-30'])`: верхняя граница там может исключить почти весь последний день. Не строить месяцы шагами в 30 дней или годы в 365 дней.

## 4. Учебная архитектура

Сохранить простой слой **Controller → FormRequest → DTO → Service**, который уже применяется в проекте, если проверка репозитория это подтвердит. Разделить предметные сервисы: `MerchantStatisticsService` отвечает за статистику конкретной кассы; `AdminStatisticsService` — за область данных и обе административные группировки. Действительно общие механизмы вынести в небольшие классы; не строить универсальный `StatisticsService`, repository или движок аналитики.

Предлагаемые имена (после проверки актуальной структуры проекта):

```text
app/Http/Requests/Statistics/TerminalStatisticsRequest.php
app/Http/Requests/Statistics/AdminStatisticsRequest.php
app/Http/Controllers/TerminalStatisticsController.php
app/Http/Controllers/Admin/StatisticsController.php
app/Data/Statistics/TerminalStatisticsData.php
app/Data/Statistics/AdminStatisticsData.php
app/Services/Statistics/MerchantStatisticsService.php
app/Services/Statistics/AdminStatisticsService.php
app/Services/Statistics/Periods/PeriodStrategy.php
app/Services/Statistics/Periods/DayPeriodStrategy.php
app/Services/Statistics/Periods/MonthPeriodStrategy.php
app/Services/Statistics/Periods/YearPeriodStrategy.php
app/Services/Statistics/Periods/PeriodStrategyFactory.php
app/Services/Statistics/PeriodSeriesFiller.php
```

Тонкие HTTP-контроллеры, policy/gate, маршруты, миграция права и тесты располагаются по существующим соглашениям репозитория. `PeriodSeriesFiller` — название, которое наглядно показывает задачу. Не заводить дополнительный helper для двух строк арифметики без потребности; округление при необходимости выделить в небольшую чистую функцию и отдельно проверить тестом.

### Контракт Strategy

Компактный контракт (ориентир для реализации, не обязательные дословные сигнатуры):

```php
interface PeriodStrategy
{
    public function name(): string;                 // day | month | year
    public function sqlBucketExpression(): string;  // фиксированное выражение для payments.created_at
    public function periodKey(DateTimeInterface $date): string; // YYYY-MM-DD начала периода
    public function nextStart(CarbonImmutable $start): CarbonImmutable;
}
```

Фабрика принимает только `day|month|year` и возвращает нужную стратегию. Один и тот же закрытый список значений использовать в валидации и фабрике. Стратегия отвечает за календарное начало бакета, его ключ и шаг к следующему; общий `PeriodSeriesFiller` и/или фабрика строят ось от периода, содержащего `from`, до периода, содержащего `to`. Не использовать `normalizeRange()` с `whereBetween`: границы дат рассчитываются отдельно один раз для всех стратегий. Не внедрять универсальную строку SQL-колонки из пользовательского ввода: выражения SQL фиксированы/проверены для конкретной схемы.

### Запросы и расчёт

1. Опираться на `Payment::query()` и Laravel builder (`where`, `join`, `selectRaw`, `groupByRaw`). Стратегия даёт только заранее определённый фрагмент группировки PostgreSQL; даты и ID передавать параметрами. Не подставлять значения HTTP-запроса в сырой SQL.
2. Для мерчанта ограничить успешные платежи авторизованной кассой и полуоткрытым временным интервалом; получить `COUNT(*)` и `SUM(amount)` по бакету. Для администратора отдельно получить множество подходящих сущностей за диапазон, отсортировать/пагинировать их, затем агрегировать платежи только выбранных сущностей по бакету. Не загружать все объекты Payment.
3. Для `group_by=user` агрегировать суммы и количество **сразу на уровне пользователя и периода**. Нельзя усреднять средние чеки касс или суммировать округлённые доходы касс: из-за веса и округления получатся другие значения.
4. PostgreSQL может вернуть `SUM`/`COUNT` строками. Проверить преобразование к целому и переполнение; не переходить к `float`. Средний чек и доход вычислять из необработанных суммы/количества после выборки. Пустой бакет: сумма, количество, средний чек и доход равны нулю.
5. `PeriodSeriesFiller` строит список бакетов один раз, индексирует агрегаты по `(entity_id, period_start)` или по одному ключу для мерчанта, подставляет нули для отсутствующих дат. Гарантировать сортировку по времени и стабильный порядок сущностей. Количество SQL-запросов зависит от пагинации, а не от числа бакетов или касс.

### Обязательная матрица проверок

- День/месяц/год на обоих маршрутах; правильное число периодов; частичные месяц/год, переход года и високосный день.
- Только успешные платежи; чужая касса не попадает в мерчантский результат; при `group_by=user` суммы/количество агрегированы корректно по нескольким кассам.
- Нижняя граница включается; весь день `to` включается; начало следующего дня исключается. Даты в PHP и PostgreSQL дают одинаковые бакеты в реальной конфигурации времени.
- Нулевые периоды в начале, середине и конце; полностью пустой ряд выбранной кассы; пустой список административных сущностей.
- Проверка дохода 10% и среднего чека на нечётных суммах, в том числе на половине тийина; в JSON денежные значения целочисленные. Отдельно убедиться, что пользователю считают доход из общей суммы, а не из округлений по кассам.
- Гость 401; запрещённый доступ согласно существующей модели прав 403 или 404; поддержка в рамках согласованных прав; забаненный пользователь может работать только с поддержкой; несуществующий ID 404.
- Отсутствующие и неправильные параметры, переставленные даты, слишком длинный ряд, недопустимая пагинация; нельзя изменить область данных параметром `user_id` мерчанта.
- При `SoftDeletes` проверить сохранение истории и ограничения владения, если эта семантика принята. Не раскрывать секрет кассы или лишние поля пользователя.
- Стабильная пагинация административных сущностей, заполненный ряд на каждой странице, разумное постоянное число SQL-запросов при росте числа сущностей. GET-запросы не изменяют БД и не влияют на существующие функции платежей и вывода.

## 6. Проверка перед завершением

- Запускать тесты в **реальном контейнере проекта и из правильной директории**, по принятой в репозитории команде и отдельной тестовой базе PostgreSQL. Ориентиры из исходного плана: `php artisan test --filter=Statistics`, тесты `Period`, полный `composer test`, `php artisan route:list --path=statistics -v`, Pint для затронутых PHP-файлов. Не предполагать неизменность команды `docker compose exec -T -u www-data php` до проверки compose-конфигурации.
- Проверить миграцию нового permission и откат **в изолированной тестовой среде**, если миграция потребовалась; не модифицировать исторические миграции. Сначала посмотреть планы SQL-запросов с репрезентативными данными, а дополнительный индекс добавлять только при обоснованной необходимости.
- Кратко описать параметры, форму JSON, статус successful-only, дату создания вместо даты оплаты, время, округление и последствия soft delete. В отчёте о выполнении указать реальные команды, результаты и оставшиеся допущения.
